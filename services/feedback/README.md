# Revclip feedback Worker

Small public JSON-to-Telegram relay. Native Workers fetch and rate-limit bindings;
no runtime dependencies, Worker storage, client secret, agent execution, or queues.
Accepted reports are forwarded to Telegram, where recipient access and retention apply.
All code and configuration in this directory are local candidates, not evidence
of deployment. The deployment owner handles account inventory, secrets, recipient
verification, publication, and production acceptance.

Planned endpoint:
`https://revclip-feedback.sasuketorii-business.workers.dev/report`

## Contract

- `GET /health` returns `200 {"ok":true}` without reading environment values or
  invoking any binding. It proves liveness only, even when reporting is disabled.
- `POST /report` accepts `application/json` (optionally `charset=utf-8`). No query
  parameters, compression, form encoding, or other routes are accepted.
- The JSON must contain exactly **eight** properties: seven strings `title` (120),
  `description` (2500), `contact` (200), `app_version` (100), `os_version` (100),
  `language` (100), `timezone` (100), plus `source_info_consent` set to the boolean
  **`true`**. All string limits count UTF-16 code units (JavaScript `.length`);
  an emoji outside the BMP counts as two. Title and description cannot be blank;
  other strings may be empty when unavailable. Unknown, missing, duplicate and
  incorrectly typed fields are rejected. False or missing consent returns 400
  after the operational and anti-abuse gates pass, with no Telegram request.
- Incoming UTF-8 is strictly decoded. The streaming body cap is 16 KiB even when
  Content-Length is missing or understates the payload. Lone surrogates are
  rejected. The complete Telegram message fits 4096 UTF-16 code units, a
  conservative bound that also bounds code points. User fields, including the
  description, are never silently truncated; over-limit input is rejected.
- The only success response is `200 {"ok":true}`, after Telegram returns HTTP
  200 and JSON boolean `ok: true`. No message IDs or other Telegram data return.
- Errors have `{"ok":false,"error":"<fixed_code>"}`: 400 invalid input,
  408 input timeout, 413 body too large, 415 unsupported content type/encoding,
  429 rate limited, 502 upstream failure, 503 disabled/config/binding failure,
  or 504 upstream timeout. Other routes return 404; other report methods 405.
  Every response uses `Cache-Control: no-store`.

This is intentionally a public native-app endpoint. There is no counterfeit
client authentication, bearer token, Origin-based identity, or CORS-based access
control. The server chooses both the upstream origin and recipient. A caller
cannot provide a chat ID, Telegram method, URL, parse mode, or limit key.

## Consent and source information

Client integration must show a required, initially **unchecked** consent checkbox,
and CLI integration must require an explicit consent flag. Explain before submission
that the report forwards IP, approximate geography, network/ASN, language, timezone,
app/OS versions, and optional User-Agent to the fixed Telegram recipient. These client
controls are implemented by the main application owner. The Worker only enforces
literal `source_info_consent: true`; this public API cannot prove a human checked a box.
Language, timezone and app/OS strings are generated by the client, not verified identity.

After validation and consent, the Worker appends `CF-Connecting-IP` and Cloudflare
`request.cf` values for `country`, `region`, `city`, `asOrganization`, and numeric
`asn`. Missing or invalid metadata becomes `n/a`. It optionally appends User-Agent,
labelled client-supplied. It ignores caller geo/forwarding headers and rejects extra
body source fields; clients cannot choose the source values through JSON. Cloudflare
metadata is approximate and is not a person or device authentication mechanism.

Diagnostic limits in UTF-16 units are IP 45, country 8, region 40, city 40,
AS organization 80, ASN 20, and User-Agent 300. Diagnostics remove control/bidi
formatting characters, replace malformed Unicode, and shorten with an ellipsis
without splitting surrogate pairs. The remaining 4096-unit message budget may
further shorten diagnostics. This never shortens the user's description.

The IP rate gate processes the edge IP **before** body parsing or consent validation
for anti-abuse. Consent gates forwarding report/source information to Telegram;
it does not prevent normal network processing or platform invocation metadata.
No Worker report database or application logs are created. Telegram and platform
metadata retention are separate from this lack of Worker storage.

## Configuration handoff

Only two secrets: `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID`. Both are supplied by
the deployment owner. Tokens are validated as a bot-token-shaped string; the
recipient is a fixed numeric chat ID string (negative group IDs supported).
Secret values are absent from configuration, fixtures and documentation.

`FEEDBACK_DISABLED` defaults to `"true"`. Only the exact string `"false"` enables
reporting; missing, mistyped and non-string values remain disabled. Missing or
malformed secrets or rate bindings also fail closed. No secrets are inspected
by `/health`.

Bindings in `wrangler.json`:

| Binding | Key | Rate |
| --- | --- | --- |
| `REPORT_IP_LIMIT` | Cloudflare's `CF-Connecting-IP`, prefixed `report:ip:` | 1 / 60 seconds |
| `REPORT_GLOBAL_LIMIT` | Constant `report:all` | 20 / 60 seconds |

The IP gate runs before body parsing; the aggregate gate runs after validation,
before sending. Failed or timed-out sends consume these gates; there is no retry,
refund, deduplication store, or delivery guarantee. A timeout may occur after
Telegram has accepted a message, so a subsequent user submission could duplicate
it. Each binding operation, incoming-body read and complete outgoing request
(including response body) has an eight-second deadline. The upstream request is
aborted on timeout. Fetch uses `redirect: "manual"`; 3xx responses fail the strict
HTTP-200 check without following Location. workerd rejects `redirect: "error"`
before sending, so that value must not be used. There is exactly one send attempt.
Upstream response reads are capped at 64 KiB.

The two namespace IDs are explicit account-scoped candidates. Before deploying,
the owner must confirm they do not collide with unrelated Workers; namespaces
with the same ID share counters. No account API was queried by this implementation.

**Residual limits:** Cloudflare's native counters are local to each Cloudflare
location and eventually consistent. The constant-key aggregate gate is not an
exact worldwide 20/minute limit. Multiple locations and concurrency can exceed
that aggregate; shared IPs can block legitimate users. There is no storage-based
strict global limiter or authentication fallback. The public edge must provide
`CF-Connecting-IP`; alternate ingress or same-zone Worker chains need their own
review of header semantics.

The runtime uses features compatible with the Workers Free resource envelope;
current official binding documentation specifies no paid-only prerequisite.
This is not a claim of a deployed Free plan: the owner confirmed the existing
account is Workers Paid ($5/month), and no plan upgrade is requested. The local
config explicitly caps CPU at 10 ms. Account quotas and included usage remain the
deployment owner's responsibility.

Observability is enabled at 10% head sampling for invocation logs. Distributed
traces are explicitly disabled to avoid recording the token-bearing outgoing
URL in automatic subrequest spans. Application code emits no logs and never
returns upstream bodies, URLs, exceptions, chat IDs, or tokens. Platform
invocation metadata can still contain incoming URLs and request metadata; keep
report/contact data in the POST body, not URLs. This configuration does not
claim control over separate account-level Logpush or Tail consumers.

## Local verification

From this directory:

```sh
npm ci
npm test
```

Tests use synthetic secrets, rate-binding mocks, native Request/Response streams,
and an injected fetch. Timeout tests accelerate the scheduler while asserting
the configured eight-second deadline. No Cloudflare API, Telegram request,
credential file, deploy, or live message is used. These tests are local contract
checks, not measurements of Cloudflare's CPU budget or deployed rate enforcement.

The required `test/workerd.test.js` exercises actual native fetch using the
lockfile-pinned Miniflare development dependency. No environment override or skip
is allowed: missing dependencies fail the suite. Its outbound service intercepts
every request locally, using synthetic bindings to check HTTP-200 success and 302
rejection with exactly one send attempt. No external upstream is contacted.
Node-only fetch mocks do not validate workerd's supported fetch options.

Miniflare is pinned to `5.20260915.0-alpha` solely for local/CI tests. The latest
stable 4.x runtime failed to start with production's `2026-09-15` compatibility
date, so this pin preserves the actual compatibility setting. It adds no Worker
runtime dependency. CI uses Node 24, runs `npm ci` and then `npm test` with
`services/feedback` as its working directory.
