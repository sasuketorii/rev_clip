# 0.0.30: 起動時のCPU負荷の修正

0.0.29では、起動時の履歴メニュー構築が画像を含む保存本文を先読みしていました。さらに`RCStorageCipher`の`Data(NSData)`がSwiftの`Sequence<UInt8>` initializerを選択し、全体を1バイトずつ取得・コピーしていました。暗号化判定と復号準備でこの変換を2回実行していました。

0.0.30では次のように変更しています。

- `NSData`から`Data`へは`as Data`で変換し、入力サイズは変換前に検査する。
- 暗号化形式の判定は先頭5バイトだけを読む。AES-GCMの認証、鍵、保存形式、保存後の検証は維持する。
- メニューの構築だけでは本文・サムネイルを読み込まない。本文はテキスト／URL／リッチテキスト項目のハイライト時、サムネイルは開いたメニューの直下の項目に限って読み込む。
- サムネイルは直列のutilityキューで処理し、キャッシュ済み画像を共有する。本文もutilityキューで処理し、読み込み中にメニューが再構築されても新しい項目は完了を待って更新する。

## 検証

macOS 26.6.2、Apple M2 Max、Xcode 26.6、最適化有効の同一条件で、`RCStorageCipher`の実コードに合成データ8MiBを渡し、一時ファイルへの暗号化保存と復号読み込みを比較しました。テスト用の一時鍵を使い、復元内容が入力と一致することを確認しています。

| 処理 | 0.0.29 | 0.0.30 |
| --- | ---: | ---: |
| 保存（暗号化・復号による検証を含む） | 4.952秒 | 0.012秒 |
| 読み込み（判定・復号） | 3.304秒 | 0.007秒 |
| 合計 | 8.256秒 | 0.019秒 |

単一のローカル測定であり、アプリ全体の改善倍率や他機種での時間を保証する数値ではありません。

`make -C src/Revclip test`で以下の回帰を検査します。

- 大きな暗号化データの往復と、バイト単位の列挙回数／判定時の読み出し量。実時間の閾値に依存しません。
- 履歴メニュー構築時の本文・サムネイルI/Oゼロ、ハイライトした項目だけの本文取得、画像本文の取得ゼロ、閉じたフォルダのサムネイル取得ゼロ。
- 同じ画像の重複生成防止、同じ本文を読み込み中にメニュー項目が置き換わった場合の完了反映。
- 既存の暗号認証失敗、ファイル境界、保存・移行、メニュー等のテスト。

遅い変換、起動時先読み、読み込み完了を待たない動作を意図的に戻すと、対応する3種類の回帰テストが失敗することも確認しました。再発調査では、CPU使用率だけでなくmacOSの`cpu_resource`診断と実行バイナリのUUID・呼び出し経路を照合してください。
